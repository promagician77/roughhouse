Decoupled Architecture

The combat simulation runs on its own fixed 60Hz tick. UE5 renders what the sim tells it.

UE5 Presentation Layer
Renderer
Draws character meshes, environments, post-processing from sim state
Camera
3D brawler camera: target switching, spacing, impact zoom
VFX / Niagara
Smears, afterimages, impact frames, hit-stop effects
Audio
Impact sounds, ambient, UI feedback, timed to sim events
HUD
Health bars, round state, combo counter, debug overlay
Render state (positions, anim frames, VFX triggers)
60Hz Combat Simulation Layer
State Machine
Per-character FSM: idle, attack, block, stun, airborne, recovery
Hitbox Manager
Activates/deactivates hitboxes per frame, resolves overlaps
Damage Calc
Scaling, combo proration, directional modifiers
Combo System
Input buffer, cancel windows, chain rules, juggle tracking
Anim Driver
Simplified animation state owned by sim, not UE5 AnimInstance
Game state / validated inputs
NET Network Layer
Input Manager
Collects local inputs, receives remote, applies input delay
State Snapshots
Ring buffer of ~8 frames: positions, velocities, hitbox phases, anim indices
Rollback Controller
Detects misprediction, restores snapshot, re-simulates forward
Desync Detector
Hashes game state each frame, compares with remote peer
Session Manager
Peer connection, matchmaking hook, spectator relay
Why decoupled? UE5's Chaos physics uses non-deterministic floating-point math. Two machines simulating the same frame from the same state will diverge. Rollback requires identical re-simulation. By running gameplay-critical collision and state on a fixed-timestep layer with deterministic math, the sim produces the same result on every machine. UE5 handles what it's built for: rendering, VFX, audio. The engine draws what the sim tells it, not the other way around.

Animation driver: UE5's default AnimInstance holds internal blend weights that aren't trivially serializable for snapshot/restore. The sim owns a simplified driver that tracks animation state as discrete frame indices and phase enums, separate from the visual AnimGraph. The renderer interpolates the visual result.

Development Milestones

Four-phase plan aligned with the RoughHouse GDD. Each phase delivers a reviewable result before the next is funded.

01
Technical Foundation
Establish the project and prove the basic gameplay direction.
  • Organized UE5 project and gameplay framework
  • Basic player movement and camera
  • Placeholder combat test with two mannequins
  • Written rollback technical proposal
  • Initial project documentation
Acceptance: Project opens, runs, demonstrates movement and combat foundations.
02
Two-Character Prototype
Make the two fighters playable using core combat mechanics.
  • Two playable character setups
  • Basic attacks and defensive mechanics
  • Hit detection and damage
  • Initial combo and launcher functionality
  • Hit reactions and knockdowns
  • Functional combat test arena
Acceptance: Both characters fight in a repeatable test, combat actions work as intended.
03
Character Art & Animation
Establish the game's visual identity.
  • Original 3D models for two fighters
  • Rigging and animation integration
  • Foundational animation sets
  • Dynamic smears and afterimage effects
  • Combat impact feedback and environment art
Acceptance: Assets integrated into UE5, function correctly during gameplay.
04
Multiplayer & Polish
Validate networking and refine the prototype.
  • Rollback implementation per approved plan
  • Multiplayer test build and network testing
  • Combat tuning and animation refinement
  • Performance and stability improvements
  • Updated documentation and project handoff
Acceptance: Multiplayer tests pass under documented conditions, final build meets milestone requirements.
